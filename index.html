Editor and Blueprint quickstart

Prerequisites: Install Dialogue through the Epic Games Launcher for your supported engine version, enable it in Edit → Plugins, and restart the editor. Use a Blueprint project with a player Pawn and an NPC Actor.

  1. In the Content Browser, choose Add → Miscellaneous → Data Asset, select Dialogue Tree, and name your conversation asset.
  2. Double-click the asset to open the Dialogue Editor. Author a root line and at least one option; set that option's Action to End for a simple exit. Save the asset.
  3. Open your NPC Actor Blueprint, add a Dialogue Speaker component, assign the asset to Default Dialogue, and set a stable Speaker ID, such as VillageGuide. Add a Dialogue Speaker component to your player Pawn Blueprint and set its Speaker ID to Player.
  4. Choose Per Player or Shared in Project Settings → Plugins → Dialogue State → Default Progress Mode. Per Player is the default. To choose differently for one NPC, enable Override Progress Mode on its speaker component, then select Per Player or Shared in Progress Mode.
  5. Add exactly one Dialogue Participant component to your Player Controller Blueprint. In your Game Mode Blueprint, set Player Controller Class to it and Default Pawn Class to your player Pawn. Select that Game Mode in Project Settings → Maps & Modes → Default GameMode; check that your level's World Settings → GameMode Override uses it or is None.
  6. For a network game, enable Replicates on the NPC and player Pawn actors. Keep Component Replicates enabled on both Dialogue Speaker components and on the controller's Dialogue Participant. These settings share the required actor and component information between server and players.
  7. In your local player's interaction event, use Create Widget with the Dialogue Window Widget class and your owning Player Controller. Use Add to Player Screen.
  8. Get the Dialogue Subsystem from the Game Instance, then call Start Dialogue Between Speakers For Player. Connect the NPC's speaker to Target Speaker. From the same owning Player Controller, use Get Controlled Pawn, then Get Component by Class with Dialogue Speaker as the class, and connect it to Instigator Speaker. Connect that controller and the widget to the remaining inputs.
  9. Check the returned Boolean. On failure, remove the widget and check the participants, controller, and tree asset before trying again. For a network game, use Get Session For Player and bind On Request Status Changed before starting; a true return means queued, and Accepted confirms the server started the conversation.
  10. Play your own level and trigger the interaction. Choose your response and check that the window closes. Save and reopen the project to verify your assignments persist.

Expected result: Your interaction opens a dialogue window showing the authored line and response. Choosing the response ends the conversation and returns control to your game.

Connect this event to your project's own Input Action or interaction system. Optional source compilation and C++ integration are covered in the advanced reference.

Overview

Dialogue is a self-contained Unreal Engine code plugin for authoring and playing hierarchical conversations. A conversation is stored in a UDialogueTree data asset. Each node chooses a speaker, presents dialogue text, and exposes player options. Options can continue into nested nodes, go back, restart, end the conversation, or jump to an authored node ID.

Purpose-built tree editor

Navigate a compact node-and-option hierarchy, edit the selection in a Details panel, and import a supported JSON subset.

Runtime subsystem

Start and close dialogue, select visible options, read the current node, and subscribe to node, option, and event delegates.

Stateful choices

Filter options with tag, stat, and counter requirements; apply effects; and consume non-repeatable choices.

Presentation helpers

Use the native widget immediately or provide your own UI. Optional camera and facing components frame active speakers.

The runtime and editor are separate modules. Your packaged game uses the Dialogue runtime module; authoring tools live in DialogueEditor and are not required at runtime.

Install and enable

  1. Install Dialogue for your supported Unreal Engine version through the Epic Games Launcher.
  2. Open your Blueprint project. In Edit → Plugins, find Dialogue under Gameplay, enable it, and restart when prompted.
  3. In the Content Browser settings, enable Show Plugin Content to see the example and plugin assets.

Author dialogue trees

Create or open a tree

  1. Create a Data Asset whose class is Dialogue Tree, or duplicate the supplied example tree.
  2. Double-click the asset to open the Dialogue Tree Editor. You can also open Window → Dialogue Editor; opening a saved asset is preferable when authoring production content.
  3. Select a node or option in the left hierarchy. Edit its reflected properties in the Details panel.
  4. Use Add Option, Add Sibling, and Delete Option from the toolbar or context menu to shape the tree.
  5. Save the asset and test every reachable path in Play In Editor.

Editor appearance settings

Open Edit → Project Settings → Plugins → Dialogue Editor to customize the hierarchy's Node Text Color and Option Text Color. These settings correspond to UDialogueEditorSettings::NodeTextColor and OptionTextColor; they affect editor tree-row text only and do not change runtime dialogue UI colors.

Flow actions

Action Result Authoring note
Next Enters the option's nested NextNode. The nested child is the normal hierarchical path.
Back Returns to the previously visited node, or closes if no previous node exists. The stack records runtime traversal, not editor parentage alone.
Start Returns to the tree's root and clears traversal history. Useful for hub-style conversations.
NodeId Jumps to a node whose authored NodeId matches JumpNodeId. Node IDs must be non-empty and unique inside the tree.
End Closes the conversation and restores input, view target, and facing policy. No child node is used.

Requirements, effects, and events

Options can require tags, compare float stats, or compare integer counters. Combine multiple requirements with All (AND) or Any (OR). Options hidden by requirements are omitted from the visible index list, so always pass the index shown by GetCurrentNode().Options back to SelectOption.

Node entry effects and option effects can add or remove tags, set or add stats, and set or add counters. Event tags authored on nodes and options are broadcast through OnDialogueEventTriggered; notification effects can use the same delegate after applying their state change.

Stable identity matters Node and option GUIDs support save-related behavior such as consumed non-repeatable choices. Let the editor generate them, keep assets under source control, and avoid rebuilding released trees in ways that arbitrarily replace those identifiers.

Speaker setup

  1. Add a Dialogue Speaker component to the player or interacting pawn and to each conversational actor.
  2. On the target actor, assign Default Dialogue. Optionally assign a Speaker Data asset for a friendly display name and portrait data.
  3. Set a stable Speaker ID. Each NPC or ByTag speaker needs a unique ID in its world; each player's own Pawn may use Player. Reuse an NPC's ID when respawning it so saved progress resolves to the same speaker.
  4. The target NPC chooses the conversation's progress mode. Use the project Default Progress Mode, or enable Override Progress Mode and select Progress Mode on its speaker. A running conversation keeps the mode it started with.
  5. Use a unique Speaker Tag when nodes or state operations resolve a participant with ByTag.
  6. If camera framing is wanted, add and place a Dialogue Camera component on the actor that supplies that view.
  7. If a specific component should define face/camera focus, add a Component Tag to that scene component and add the same name to Focus Component Tags. Otherwise actor bounds provide the focus point.

Custom UI

The start call requires a non-null UUserWidget. Choose Dialogue Window Widget in Blueprint's Create Widget node for the included interface. For a custom interface, use Get Session For Player with the owning Player Controller, bind that session's On Dialogue Node Changed, render the supplied node view, and call the same session's Select Option with the selected visible index. Use Add to Player Screen and handle closure in your own widget lifecycle.

The included window wraps long dialogue lines in a scroll area separate from the response list. Use its scrollbar or pointer wheel. With focus on the window or a response button, Page Down or the gamepad's Right Shoulder reads further down; Page Up or Left Shoulder returns to earlier text. Changing nodes starts the text at the top.

These built-in keys read the owning player's text while that conversation is active; they do not choose a response. If you replace the native body with a custom layout, provide suitable scrolling and controls so all text remains reachable.

Blueprint and C++ integration

Blueprint orientation

  1. Get the Dialogue Subsystem from the Game Instance.
  2. Use Get Session For Player with the owning Player Controller. Bind that session's On Dialogue Node Changed and On Request Status Changed.
  3. Create your dialogue widget with the same owning Player Controller and use Add to Player Screen.
  4. Call Start Dialogue Between Speakers For Player with the target and instigator Dialogue Speaker components, widget, owning Player Controller, and the input mode to apply after close.
  5. In a network game, a true start result means the request was queued. Wait for Accepted before treating the conversation as active. Use the request status message to explain denials such as another player using a Shared speaker or being out of range.
  6. Call the owning session's Select Option with a visible option index, or let the included widget handle selection.
  7. Call that session's Close Dialogue for cancellation. Check its Is Dialogue Active and Is Request Pending when managing interaction state.

Optional advanced C++ start

#include "DialogueSubsystem.h"
#include "DialogueSpeakerComponent.h"
#include "UI/DialogueWindowWidget.h"
#include "Engine/GameInstance.h"
#include "GameFramework/PlayerController.h"

bool StartConversation(
    APlayerController* PlayerController,
    UDialogueSpeakerComponent* Target,
    UDialogueSpeakerComponent* Instigator)
{
    if (!PlayerController || !Target || !Instigator)
    {
        return false;
    }

    UGameInstance* GameInstance = PlayerController->GetGameInstance();
    UDialogueSubsystem* Dialogue =
        GameInstance ? GameInstance->GetSubsystem<UDialogueSubsystem>() : nullptr;
    if (!Dialogue)
    {
        return false;
    }

    UDialogueWindowWidget* Window =
        CreateWidget<UDialogueWindowWidget>(PlayerController);
    if (!Window)
    {
        return false;
    }

    Window->AddToPlayerScreen();
    const bool bStarted = Dialogue->StartDialogueBetweenSpeakersForPlayer(
        Target,
        Instigator,
        Window,
        PlayerController,
        EDialogueInputModeAfterClose::GameOnly);
    if (!bStarted)
    {
        Window->RemoveFromParent();
    }
    return bStarted;
}

Network setup

Add exactly one Dialogue Participant component to the Player Controller Blueprint used by the active Game Mode. The server receives requests through that player's controller and uses its possessed Pawn as the instigator. Use Get Controlled Pawn from the owning controller to find that Pawn's speaker; do not pass another player's Pawn. Enable actor Replicates on NPCs, player Pawns, and speakers addressed by tag. Keep Component Replicates enabled on their Dialogue Speakers and the controller's Dialogue Participant, including Blueprint-derived replacements. Assign the same cooked Dialogue Tree assets to the server and clients.

For placed NPCs, enter a unique Speaker ID on each speaker component. For Blueprint-spawned NPCs, expose an ID variable on spawn and call Set Stable Speaker ID on the server before the first interaction. The speaker component replicates that ID with its actor. IDs must be nonempty and use at most 128 UTF-16 code units; most ordinary letters use one unit. They cannot change through this node after progress begins. Keep saved IDs stable across loads; give different persistent NPCs different IDs.

Set Max Interaction Distance on each target speaker in centimeters; the default is 500 cm. The server checks this distance at start and while the conversation runs.

For game-specific restrictions, create a Blueprint Class, open All Classes, and select Dialogue Participant as its parent. Override Can Start Dialogue and Can Continue Dialogue in that component Blueprint; the server calls these checks. In your Player Controller Blueprint, replace the plain Dialogue Participant component with this component Blueprint. Keep exactly one participant component and leave Component Replicates enabled.

The server runs requirements and effects. Only the owning player receives the conversation view, choice tokens, notifications, and relevant progress. Other players' screens, camera, audio, and controls stay independent. Bind server gameplay to the Participant's authority delegates and local feedback to the owning session's presentation delegates. Hosting, matchmaking, accounts, and durable saves belong to your game.

Camera and facing behavior

Camera framing and actor facing are optional runtime helpers. They activate only while dialogue needs them and restore their captured gameplay state when the conversation closes.

Dialogue camera

  • Add a UDialogueCameraComponent to the actor that should provide a dialogue point of view.
  • Place and rotate it like a regular Camera component. Configure enter/exit blend times and functions on the component.
  • When Aim At Other Speaker is enabled, the temporary rig follows the source camera's position and smoothly aims at the other speaker's focus location.
  • If no usable Dialogue Camera exists, the dialogue can still run; design your normal camera behavior accordingly.

Speaker facing

  • Turn Towards Other Speaker is controlled per speaker. Disable it for actors that must retain authored rotation.
  • Turn Ease Duration controls response time; zero snaps. Ease Exp shapes the settle.
  • For Characters, the helper temporarily adjusts movement/controller-yaw policy and restores the saved policy on close.
  • Per Player mode leaves the shared NPC's facing unchanged so simultaneous conversations cannot fight over its rotation. In networked Shared mode, the server can turn the NPC when its movement replicates; it does not turn a player-controlled Pawn.
  • Always test with your movement, root-motion, animation, and controller stack. Systems that continuously write actor rotation can compete with dialogue facing.
Close every exit path Use CloseDialogue for cancellation, level-transition preparation, or custom teardown. The subsystem also cleans up during deinitialization, but explicit closure gives your UI and gameplay state a predictable lifecycle.

Dialogue state and save restoration

Choose Default Progress Mode in Project Settings → Plugins → Dialogue State. To override it for an NPC, enable Override Progress Mode and select Progress Mode on the target's speaker component:

  • Per Player: each Dialogue Participant keeps its own record for each Speaker ID. Two players can use the same NPC concurrently. One player's consumed choices, tags, stats, counters, and future dialogue do not change the other's record.
  • Shared: everyone uses the speaker component's Persistent State. Only one conversation can use that target at a time. A competing network start receives Busy; a competing standalone start returns false. Show the rejection through On Request Status Changed in network UI. After the first conversation closes, try a new start request.

The server reads the target's mode when a conversation starts and uses it for all speakers in that conversation. A running conversation keeps that mode; a later start uses the new setting. Per-player records start from the speaker's initial state on first use. Importing saved progress takes precedence. Changing the mode does not merge or copy existing records between modes. Both modes use FDialogueSpeakerPersistentState, which contains:

  • Stats: named float values.
  • Counters: named integer values.
  • Tags: named boolean-like flags.
  • ConsumedOptionGuids: identities of selected non-repeatable options.
  • CurrentDialogueOverride: an optional soft reference to the tree used on future interactions.

The UDialogueStateBlueprintLibrary provides Has/Add/Remove Tag, Get/Set/Add Stat, Get/Set/Add Counter, option consumption, and Clear All operations on a state struct. In a network game, edit the speaker's Persistent State on the server to change Shared progress. Editing a client's copy does not update the server. To change saved Per Player records outside a conversation, export them on the server, edit their state structs, and import them again.

Stat writes accept only finite values and additions saturate at the finite float range; counter additions saturate at the 32-bit integer bounds instead of wrapping. Runtime dialogue effects apply the same safety before an optional definition-table clamp. Configure stat and counter definition DataTables under Project Settings → Plugins → Dialogue State; row names identify values and can supply defaults, clamping, and stat-change messages.

Referenced stat rows need finite defaults. When clamping is enabled, stat bounds must be finite and both stat and counter bounds must have a minimum no greater than the maximum. A conversation rejects invalid definitions before applying effects. Table edits made during a callback take effect on the next conversation operation.

Saving

  1. Create a Blueprint derived from SaveGame. For Per Player progress, add a variable named DialogueProgress, set its type to Dialogue Speaker Progress Record, and change it to an Array. For Shared progress, add speaker-state variables keyed by stable speaker IDs.
  2. For Shared progress, save each relevant speaker component's Persistent State. Restore it on the server, then call Apply Persistent Dialogue Override if the component has already begun play.
  3. For Per Player progress, on the server call Export Progress on that player's Dialogue Participant. Connect the returned array to Set DialogueProgress on your SaveGame object, then use your game's Save Game to Slot flow for that player.
  4. After Load Game from Slot, cast the loaded object to your SaveGame Blueprint. On the server, connect its DialogueProgress array to Import Progress on the participant belonging to the same player. Use a Branch on the returned Boolean: start dialogue only after a successful restore, and handle failure in your save flow. Import is rejected while that participant has an active conversation or state provider.
  5. Resolve versioning in your save model when renaming stat IDs, counter IDs, tag IDs, speaker IDs, tree assets, or released dialogue options.

Import replaces all records: a valid array replaces the participant's Per Player records together, so include every record you want to keep. A valid empty array clears them. A false return leaves the previous records unchanged. Each record needs a unique, nonempty Speaker ID within the 128-unit limit and valid state values; follow the state size limits when editing saves.

Persistence is deliberately project-owned Your game selects and writes SaveGame slots and maps player accounts to saved records. Per-player records do not automatically survive controller replacement, reconnect, or travel. Export and restore them through your game's server lifecycle. Shared progress lasts for the speaker component's lifetime unless your game saves and restores it.

Hierarchical JSON import

The Dialogue Tree Editor can import from a file or pasted text. In the asset editor's File menu, choose Import Dialogue JSON… or Paste Dialogue JSON…, then either create a new asset or overwrite the selected tree.

Overwrite replaces authored tree content Duplicate or commit the asset before importing over it. Import is not a merge operation.

Scripted editor import

Editor Utility Blueprints and editor-only C++ tools can call UDialogueEditorBlueprintLibrary::ImportJsonFileToDialogueTree for a UTF-8 file or ImportJsonTextToDialogueTree for an in-memory string. Both functions require an existing UDialogueTree; they do not open a save dialog or create an asset.

  • A true return replaces the tree's imported fields and entire root hierarchy in memory. TreeId changes only when the JSON supplies it. The package is marked dirty; your editor tool must save the asset or package.
  • A false return leaves an actionable explanation in OutError. Report that text to the user and do not save the failed import; keep the asset backed up before any overwrite workflow.
  • The library belongs to the DialogueEditor module. Use it only from editor targets or editor-only Blueprint tooling; do not add DialogueEditor to a runtime or Shipping dependency.

Supported core schema

  • The document root contains optional TreeId and required object RootNode.
  • A node can contain NodeId, Speaker, SpeakerTag when using ByTag, DialogueText, and Options.
  • An option can contain OptionText, Action, bIsRepeatable, nested object Next for the Next action, and JumpNodeId for the NodeId action.
  • Optional state and event fields are also supported: NodeEventTags, EntryEffects, RequirementLogic, Requirements, Effects, and OptionEventTags.
  • Speaker values are Target, Instigator, or ByTag. Action values are Next, Back, End, Start, or NodeId.
  • A jump only references a node; it does not declare one. Every jump target must exist somewhere in the nested Next hierarchy and have a unique NodeId.

Optional state and event objects

Requirements use Type (HasTag, MissingTag, StatCompare, or CounterCompare), Target (Target, Instigator, or ByTag), and the fields needed by that type: TargetSpeakerTag, TagId, StatId, CounterId, CompareOp, StatValue, or CounterValue. Set the option's RequirementLogic to All/And or Any/Or.

Effects use Type (AddTag, RemoveTag, SetStat, AddStat, SetCounter, or AddCounter), plus the corresponding target, ID, and value fields. They can also contain bNotifyUI and NotifyTag. Put effects in a node's EntryEffects array or an option's Effects array. NodeEventTags and OptionEventTags are arrays of strings.

Importer boundaries

The importer does not resolve content asset paths or reproduce every reflected property. After import, use the Details panel to assign voice assets, future-dialogue asset references, and any presentation data. Speaker Data assets and project-wide stat/counter definition tables are configured separately. Treat JSON as an authoring interchange for the supported hierarchy and state/event fields, not as a lossless export or general Unreal asset-serialization format.

Known schema fields are type-checked before the destination tree is replaced. A failed parse or validation leaves the existing tree fields and root hierarchy unchanged. To bound editor memory and recursion, imports accept files up to 8 MiB, in-memory text up to 8,388,608 characters, JSON nesting up to 256 levels, dialogue hierarchies up to 64 nodes deep and 10,000 total nodes, up to 256 options on one node, and up to 1,024 entries in each event-tag, requirement, or effect array. Split content into multiple Dialogue Trees if a source exceeds those authoring limits.

JSON fields stored as names, such as TreeId, NodeId, JumpNodeId, speaker tags, state IDs, and event tags, accept at most 1,023 UTF-16 code units. Most ordinary letters use one unit; some Unicode characters use two. Embedded NUL characters, including JSON \u0000, are rejected. Network conversations use a tighter 128-unit limit for their identifiers, and imported assets must meet the separate network limits before they can run online.

StatValue must be a finite 32-bit floating-point value. CounterValue must be a whole 32-bit integer; fractional, out-of-range, or non-finite numeric values are rejected with an error instead of being rounded or wrapped.

The legacy flat format with a top-level dialogues array and string next references is not this schema. Convert it to a required RootNode with nested Next objects and explicit Action values before importing.

Package your game

  1. Keep Dialogue enabled in Edit → Plugins for the target project.
  2. Reference required Dialogue assets through normal hard or soft asset references. Do not rely on an editor window having loaded them.
  3. Cook and package for your verified engine version using the editor's packaging workflow.
  4. Run a Development package first and exercise starting, every flow action, save restoration, custom UI input, camera exit, and map transitions.
  5. Run the same smoke path in Shipping. Confirm your own input, SaveGame, localization, audio, and networking policies.

The editor module should not be added to a shipping runtime dependency. Plugin content cooks when referenced, but your project's asset-management and chunking rules still apply. If you dynamically load trees only by constructed strings, add an explicit cooking rule or primary-asset policy and test the packaged build.

Known limitations and design boundaries

  • Candidate scope: Win64 is the current release target. Engine, packaged-runtime, device, and multiplayer acceptance checks remain in progress; the public support table must be finalized from their results.
  • Local-player model: each local player has a separate session. Use Get Session For Player for actions and delegates; unscoped subsystem actions and delegates address the first local player. Split-screen closure requests an input mode through On Input Mode After Close Requested; your project decides any viewport-wide input policy.
  • Network candidate: listen-server and dedicated-server acceptance remains in progress. The implementation routes requests to the server and sends the relevant conversation view and progress to its owner. Do not treat an unexecuted mode as verified support.
  • Save storage: persistent state is a serializable data structure, not an automatic SaveGame service.
  • Input: the native window exposes clickable/tappable choices and a Close button while the Slate input preprocessor handles keyboard/gamepad navigation and cancel. The example supplies raw defaults for mouse/keyboard, gamepad, and touch; production projects should replace the interaction bindings and integrate their own remapping, accessibility, multiplayer ownership, or CommonUI behavior explicitly.
  • JSON: import covers the documented hierarchical subset and is not a lossless round trip for every asset property.
  • Localization: text imported from plain JSON is created from strings. Review your localization pipeline and stable text identity requirements before using JSON as the authoritative source for localized production dialogue.
  • Runtime tree mutation: tree assets are intended as authored content. Put mutable progress in speaker persistent state instead of modifying shared data assets during play.
  • Network presentation: one active conversation per participant; Shared mode also allows one conversation per target. Each view accepts at most 32 choices, 4,096 characters in a line, 512 characters per choice, and 8,192 presentation characters in total. A conservative 48 KiB payload estimate also includes full text histories, identifiers, notifications, and progress; unusually large formatted or localized text can exceed it even within the character limits.
  • Network progress: a tree can reference at most 16 speakers and 256 potential progress entries in total, including entries its effects can create. Each saved speaker record accepts 128 stats, 128 counters, 128 tags, and 256 consumed options, with 512 entries total; a participant accepts 1,024 records. Nodes accept 64 entry effects; options accept 64 requirements and 64 effects. Each node and each option accepts eight event notifications, including effect notifications. Network trees accept 4,096 reachable nodes. Split oversized text into shorter nodes. A tree-wide progress limit requires reducing or separating its state usage.
  • Request timing: the server accepts ten requests per second with an initial burst of twenty. An active conversation expires after sixty seconds without an accepted interaction. Your UI should handle rate-limit rejection and closure.

Troubleshooting

The plugin does not appear in Edit → Plugins

Check that the path ends in Plugins/Dialogue/Dialogue.uplugin, not Plugins/Dialogue/Dialogue/Dialogue.uplugin. Confirm that the complete plugin was copied and restart the editor.

The project will not compile after installation

Confirm that you installed Dialogue for the same supported engine version as your project. Reinstall the matching plugin through the Epic Games Launcher and restart the editor. For an optional source-based installation, use that engine's supported native toolchain; never delete Source or Content.

I cannot find the example map or assets

Enable Show Plugin Content in the Content Browser and find Dialogue's Example folder. Reinstall the matching plugin if its content is absent.

Start Dialogue Between Speakers returns false

Verify that target, instigator, and widget are all non-null; both actors use Dialogue Speaker components; the target has a current or default Dialogue Tree; and that tree has a root node. Check the Output Log for an actionable Dialogue warning.

An option does not appear

Inspect its requirements against the targeted speaker state. For a non-repeatable option, check whether its GUID is already in ConsumedOptionGuids. Remember that GetCurrentNode exposes only visible options.

A Node ID jump closes the conversation

Make sure JumpNodeId exactly matches one unique, non-empty NodeId in a node reachable through the tree's nested hierarchy. Duplicate IDs are invalid authoring and a missing destination cannot be traversed.

The dialogue UI shows but keyboard, gamepad, mouse, or touch input is wrong

First test with the included native window widget. For custom UI, create it with the correct owning Player Controller, use Add to Player Screen, focusable buttons, and an explicit close control. Check competing input preprocessors and project touch/navigation settings. Put pause or menu input above the Dialogue State setting's Modal Input Priority, which defaults to 100. Route interaction through your own input system; the raw example bindings belong to the harness.

The camera does not frame a speaker

Add a Dialogue Camera component to the relevant actor and confirm its transform. Check Aim At Other Speaker and focus tags. Without a Dialogue Camera, the runtime leaves presentation to the project's normal camera.

An actor keeps fighting dialogue-facing rotation

Animation, root motion, movement code, controller code, or another Tick may be writing rotation concurrently. Disable Turn Towards Other Speaker for that participant or coordinate ownership in project code. Always call CloseDialogue during custom teardown.

Saved choices or a dialogue override did not return

Check which progress mode the target uses. Shared mode restores the speaker's Persistent State; Per Player mode restores Export Progress records through the player's server-side Dialogue Participant. Use the same stable Speaker IDs and check Import Progress's result. Restore before starting a conversation.

JSON import fails or produces a different tree

Validate the JSON syntax and exact field names. The root must contain an object named RootNode. Use nested Next objects rather than a flat node array. Asset references such as voice sounds and future Dialogue Tree overrides are intentionally not resolved from JSON; assign those references in the editor after import.

Upgrade and migration

  1. Commit or back up your project, Dialogue assets, JSON sources, and SaveGame migration code.
  2. Close Unreal Editor and your IDE.
  3. Update the plugin for your supported engine through the Epic Games Launcher. For an optional source installation, replace the folder as a unit and keep generated output from different engines separate.
  4. Reopen your project and restart if the editor requests it. Recompilation is needed only for an optional source-based installation.
  5. Open representative released Dialogue Trees and resave only after reviewing the editor result.
  6. Test old SaveGame data, especially consumed option GUIDs and soft tree overrides, before shipping the upgrade.
  7. Retest custom widget focus, event-tag consumers, camera/facing teardown, packaged dynamic asset loads, and every JSON import pipeline.

Schema and identity changes

Older hierarchical Dialogue Tree assets that serialized bIsEnd or NextNodeId options are migrated to the current Action/JumpNodeId representation when loaded. Missing persistent node and option GUIDs are repaired deterministically. Review and resave those assets in the editor before packaging so the migrated data is stored in source control.

The earlier flat JSON format is not converted automatically. Convert it to the hierarchical schema before import. Preserve released asset paths, Tree IDs, Node IDs, and GUID-bearing tree data whenever code or saves depend on them. Migrate saved data when renaming a tag, stat, counter, speaker, or jump ID.

Do not test upgrades only with new saves Keep representative pre-upgrade saves and dialogue assets in a private regression fixture. A clean new game cannot reveal broken consumed options, renamed IDs, or missing dialogue overrides.

Privacy, telemetry, and support

Dialogue contains no telemetry, analytics reporting, account service, advertising, or tracking pixel. In a network game, it uses your game's Unreal connection to send the owning player the current conversation text, choices, notifications, and relevant progress. It does not operate an external service. Your game controls hosting, accounts, storage, and platform connections.

Support: report a Dialogue issue. Include the plugin version, engine version, target platform, reproduction steps, relevant Dialogue log lines, and whether the issue occurs in the included example map. Remove personal information and private game content before posting logs.
